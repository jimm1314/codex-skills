## 1. 使用方式

- B 级任务使用简版 Spec，并保留与任务相关的契约、验收和风险。
- C 级任务使用完整 Spec。在高风险、不可逆或架构级决策确认前，不进入实现。
- 只填写有证据或有实际风险的内容。不知道的内容标为“待确认”，采用默认值的内容标为“假设”。
- 把验收标准写成可观察、可执行或可测量的结果，避免“运行正常”“体验良好”“性能较高”。
- 认可想法或范围不等于批准计划。B/C 级计划写完并完成自检后交用户审阅，确认后再实现。

## 6. 实施任务

按依赖顺序拆分为小而可验证的任务，每步是“一个动作 + 可检查结果”：

| 任务 | 目标 | 文件 | 前置依赖 | 关键决策（签名/规格值） | 测试与断言 | 验证命令及通过输出 | 风险 |
|---|---|---|---|---|---|---|---|
| T-01 | | | 无 | | | | |

### 每步写什么

计划记录实现者无法自行决定的事项，不是代码的抄本：

- **测试步骤**：测试名和断言，带上规格中的具体值。
- **代码步骤**：所在文件、函数签名（名称、参数、返回类型）和规格固定的值；只有签名和测试无法确定的算法，或规格固定的文案，才写出函数体。
- **验证步骤**：要运行的命令和代表通过的输出。
- **引用其他任务**：指向该任务的接口定义，不重复其代码。

禁止不做决定的条目，例如“TBD”“处理边界情况”“添加适当校验”“为上述代码写测试”，或引用没有任何任务定义的类型和函数。

### 重点风险

列出规格隐含、但没有任务测试覆盖、最可能影响用户的输入类型或失败模式，最多 5 条，按可能性排序。每条写明输入或条件，以及合理用户期望的行为，并在负责该代码的任务中补上对应测试。规格没写不等于允许程序出错；确实没有时写“已检查，无”，不能跳过检查。

### 计划自检

计划交给用户前检查：

1. **需求覆盖**：每条需求和验收标准都有对应任务。
2. **无占位**：没有上面列出的不做决定的条目。
3. **一致性**：各任务中的名称、签名和数据结构一致。
4. **重点风险**：每条都已落到某个任务的测试。
5. **篇幅比例**：计划明显长于规格或以代码块为主时，把函数体换成签名与断言。

发现问题直接修正，无需再走一轮审查。

- 不在前置依赖未满足时盲目进入下一任务。
- 每个阶段完成后运行最小相关验证；最后运行项目完整测试、集成验证和回归检查。
- 命令无法运行时记录阻塞因素和替代证据，不得填写虚构结果。

## 7. 确认闸门

必须等待用户确认：

- 会改变公开接口或破坏旧版本兼容；
- 会删除或不可逆迁移数据；
- 会明显改变架构、技术栈或部署方式；
- 涉及生产环境、真实敏感数据或危险操作；
- 新项目的平台、语言或关键依赖选型，除非用户已明确交给 AI 决定；
- 多种选择会实质改变范围、成本或安全性，且无法从项目规则得出答案。

可以记录假设后继续：

- 命名、局部文件组织等低风险且易撤销选择；
- 项目已有明确惯例可直接沿用；
- 不影响公开契约和验收标准的实现细节。
