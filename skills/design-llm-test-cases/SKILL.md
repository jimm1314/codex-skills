# 大模型测试用例设计

## 遵守测评原则

1. 先澄清测评对象和标准，再设计用例。不要默认模型能力、业务规则、合格阈值或唯一正确答案。
2. 把模型名称、精确版本或快照、系统 Prompt 版本、知识库版本、工具版本、关键推理参数和测试日期视为复现条件。缺失时标记为“待确认”。
3. 对开放任务使用带锚点的评分 Rubric；只有确实存在唯一答案时才写固定答案。
4. 明确区分硬性规则与主观质量。硬性失败不得被流畅度等主观高分抵消。
5. 不输出真实密钥、内部地址、个人信息或敏感业务数据。用户提供公司数据时，先提醒其确认数据处理权限；优先建议脱敏、最小化或使用等价合成数据。
6. 先把每条用例设计成可独立执行和定位单一主要风险，再组合成端到端场景。
7. 不把一次失败直接归咎于模型。根据证据区分模型、Prompt、数据、工具、系统和评分问题。

## 第一步：澄清测评合同

优先确认以下五项：

1. **测评对象**：基础模型、对话应用、RAG、Agent、工具调用系统或完整产品；
2. **模型版本**：供应商、模型 ID、快照或部署版本；
3. **业务场景**：真实用户、任务、语言、输入输出和风险等级；
4. **测试目标**：准入验收、横向对比、版本回归、问题诊断、安全检查或上线监控；
5. **通过标准**：硬性规则、指标阈值、Rubric、人工基准或旧版本基线。

信息不足时每次只问最关键的 1～3 个问题，并提供选项。优先使用：

> 你要测的是哪一类？  
> A. 基础模型或聊天模型  
> B. RAG 问答系统  
> C. Agent 或工作流  
> D. Function Calling、MCP 或其他工具调用  
> E. 完整大模型应用

> 这次测评最主要的目标是什么？  
> A. 上线前验收  
> B. 两个模型或方案对比  
> C. 新旧版本回归  
> D. 定位当前问题  
> E. 安全与对抗检查

不要重复询问用户已经给出或能从测试规范、配置和代码中确认的信息。尚未获得关键通过标准时，只能先提出候选标准并请求确认，不能把候选项写成既定标准。

## 第二步：确定范围和能力维度

1. 阅读 [test-dimensions.md](references/test-dimensions.md)，从实际系统能力和风险中选择维度，不要机械选择全部维度。
2. 为每个纳入维度写明测试目标、业务风险、适用用户、输入范围、输出约束和不在本次范围内的内容。
3. 对复合系统分层：模型层、Prompt/编排层、检索与数据层、工具层、基础设施层、产品交互层。
4. 将无法获得的环境、权限、数据或观测信息列为范围限制。

## 第三步：建立场景矩阵

每个核心维度至少考虑以下五类；不适用时写明原因：

1. **正常场景**：典型、清晰、符合预期的输入；
2. **边界场景**：长度、数量、格式、上下文窗口、权限或业务规则临界点；
3. **异常场景**：缺字段、格式错误、超时、空结果、工具失败或依赖不可用；
4. **对抗场景**：提示注入、越权、混淆、诱导幻觉、编码变形或恶意工具结果；
5. **回归场景**：历史故障、核心黄金集、版本敏感行为和已修复缺陷。

组合输入语言、用户类型、风险等级、数据状态、工具状态和对话轮次时优先使用风险驱动或成对组合，避免无意义的笛卡尔积。

## 第四步：生成测试用例

使用稳定编号，例如 `TC-RAG-FAITH-001`。每条用例至少包含：

1. 用例编号；
2. 测试维度；
3. 场景说明；
4. 前置条件；
5. 输入内容；
6. 预期行为；
7. 禁止出现的行为；
8. 评分方法；
9. 优先级；
10. 是否适合自动化；
11. 失败归因方向；
12. 备注。

按照 [case-schema-and-rubrics.md](references/case-schema-and-rubrics.md) 填写字段和评分方式。确保：

- 一条用例只突出一个主要验证目标，必要时记录次要观测项；
- 前置条件包含模型与系统版本、参数、数据夹具、工具状态和对话历史；
- 输入可直接复制执行，动态值使用明确占位符；
- “预期行为”描述允许的行为集合、必要事实、约束或质量阈值，而非随意指定唯一措辞；
- “禁止出现的行为”可观测、可判定；
- 自动化适用性使用“是 / 部分 / 否”，并说明判定器；
- 失败归因只写初步候选方向，不在执行前宣称根因。

## 第五步：设计评分

1. 优先采用确定性检查：JSON Schema、精确字段、正则、程序执行、单元测试、工具轨迹、引用存在性和安全规则。
2. 对语义正确性、完整性、相关性、可读性等开放指标使用分级 Rubric，为每个分值写可观察锚点。
3. 先应用硬性门禁，再计算主观或加权分；明确单用例、维度和整体三个层级的通过规则。
4. 需要 LLM-as-a-Judge 时，明确提醒其位置偏差、冗长度偏差、自偏好、提示敏感性和不稳定性。固定 Judge 版本与 Prompt，交换候选顺序，使用校准集，并安排人工抽检。
5. 对非确定性模型指定重复次数、温度等参数、聚合方式和置信区间或稳定率，避免以单次输出代表全部质量。

## 第六步：检查覆盖率和重复

使用 [coverage-and-attribution.md](references/coverage-and-attribution.md)：

1. 建立“测试维度 × 场景类型 × 风险等级 × 系统层”的覆盖矩阵；
2. 检查核心业务、高风险失败、历史故障和版本变化是否都有用例；
3. 比较验证目标、前置条件、输入语义、预期行为和失败信号，合并实质重复用例；
4. 保留看似相似但能隔离不同根因或不同边界的用例，并在备注中解释差异；
5. 汇报已覆盖、部分覆盖、未覆盖和无法测试的项目，不用单一百分比掩盖关键缺口。

## 第七步：规划失败归因

按证据区分：

1. **模型问题**：相同 Prompt、数据与工具条件下，模型能力或稳定性不足；
2. **Prompt 问题**：指令缺失、冲突、歧义、示例污染或上下文编排不当；
3. **数据问题**：知识缺失、过期、错误、切分不当、召回失败或权限数据混入；
4. **工具问题**：工具描述、参数映射、协议、返回值、权限或工具自身失败；
5. **系统问题**：路由、状态管理、序列化、缓存、并发、超时、重试或观测链路异常；
6. **评分问题**：参考答案、规则、Rubric、Judge 或人工标注本身不可靠。

输出失败归因检查表，逐项列出“模型、Prompt、数据、工具、系统、评分”六类的适用状态、所需证据和隔离方法。当前系统没有某一层时明确标为“不适用”，证据不足时标为“待确认”，不要直接省略。

记录原始输入、各层中间结果、工具请求与响应、检索证据、最终输出和评分明细。缺少隔离实验时使用“疑似”而不是“已确认根因”。

## 第八步：组织交付结果

严格按以下顺序输出：

1. 当前理解；
2. 待确认问题；
3. 测试范围；
4. 测试维度；
5. 测试用例表；
6. 覆盖情况；
7. 风险和限制；
8. 下一步选择。

信息尚不足时先输出前两项并等待回答，不要用假设填满后续内容。用例较多时先给覆盖设计和代表性用例，再询问是否展开完整用例集或转换成 CSV、JSON、YAML、测试脚本等格式。

## 决定是否使用多 Agent

1. 简单、单维度或少量用例默认使用单 Agent。
2. 只有复杂、跨系统或大规模测评，并且环境允许时，才分别委派：
   - 能力维度与范围分析；
   - 测试用例生成；
   - 覆盖率和重复检查；
   - 风险、评分与失败归因检查。
3. 让各子任务基于同一份最小测评合同独立完成，不让一个子任务依赖另一个子任务的结论，也不泄露预期答案来诱导验证结果。
4. 由主智能体统一编号和字段，去重、检查冲突、补齐覆盖，并对最终质量负责。
5. 不为形式强制使用多 Agent；无法使用多 Agent 时按相同步骤单线程完成。
