# Git 与 GitLab 安全协作

## 核心原则

1. 使用通俗中文解释本次真正需要的 Git 概念。
2. 只根据真实命令输出和仓库规则下结论，标明`已确认`、`合理推断`或`尚待确认`。
3. 事实优先级：

   ```text
   当前真实 Git / 源码 > CODEX_HANDOFF.md > 历史对话或 Skill 假设
   ```

4. Handoff 只用于了解目标、关键 commit 和待办，不能证明当前 branch、工作区或远端最新状态。
5. 优先保护用户代码和可恢复性；不把 reset、clean、强推或丢弃改动作为常规方案。
6. 用户提出目标不等于同意某个具体 Git 操作。状态或方案变化后重新说明并确认。

## 不可覆盖的底线

1. **有未提交修改时不自动 merge/rebase/pull**：先识别修改归属，讨论提交、备份或 stash 等选择；用户明确选定并安全处理后再评估。
2. **不直接修改 `dev` 或 `main`**：这两个分支只做查看和远端元数据刷新。开发、提交、merge、rebase、reset、cherry-pick 或 push 前先切到合适的功能分支并取得同意。
3. **破坏性操作二次确认**：`git reset --hard`、`git clean -fd` 及变体、任何 force push 都必须单独展示影响、恢复可能和数据风险，并再次获得明确肯定。
4. 不擅自提交、推送、合并 MR、删除分支或标签，也不机械选择冲突中的 ours/theirs。

## 风险分级

### 只读检查

branch、status、diff、log、配置和引用查看不改变工作区或分支。

- Codex 可访问仓库时，可以在一次工具调用中批量执行互不依赖的只读检查并汇总，避免多轮重复。
- 用户需要手动执行时，每次只给一条命令，等待真实结果。
- `git diff` 只在存在修改或确需比较时读取；先看 `--stat`/文件列表，再按需展开。

### 刷新远端元数据

`git fetch` 需要网络和认证，会更新远端跟踪引用及 `FETCH_HEAD`，但不合并当前分支。

- 只有判断最新远端关系确有必要时才建议；
- 先说明影响并取得同意；
- 不把未 fetch 的远端跟踪引用称为“远端最新”。

### 改变本地状态

checkout/switch、add、commit、stash、merge、rebase、pull、restore、reset、cherry-pick，以及 continue/abort 都会改变本地状态。执行前说明：

- 触发原因和目标；
- 影响的分支、文件或提交；
- 冲突、历史或数据风险；
- 可恢复方式；
- 本次只执行的一个原子动作。

### 影响共享远端或可能丢失数据

push、删除远端引用、强推、硬重置、清理文件和丢弃修改需要更高保护：

- 展示准确影响范围；
- 优先提出非破坏性替代；
- 说明备份/恢复方案；
- 获得独立明确确认；破坏性操作按底线二次确认。

## 诊断流程

1. 定位目标仓库。
2. 如果存在 `CODEX_HANDOFF.md`，读取其 Git 摘要和下一步，但不据此下状态结论。
3. 检查当前 branch、`git status`、上游关系和最近 log。
4. 有修改时再检查 staged/unstaged/untracked 范围和相关 diff。
5. 检查是否存在 merge、rebase、cherry-pick、bisect 或 detached HEAD。
6. 需要判断最新远端时，说明 fetch 影响并等待授权；未刷新时标记限制。
7. 按需读取团队的贡献、分支、MR 和受保护分支规则。

诊断结束至少说明：

- 当前分支和 HEAD；
- 工作区、暂存区和未跟踪文件；
- 是否有进行中的 Git 操作；
- 上游配置；
- 基于当前证据的 ahead/behind；
- 团队策略是否已确认；
- 当前最安全的下一步。

## 提供方案

确实存在选择时给 2～3 个适用方案，每个包含：

- 适用条件；
- 好处；
- 风险；
- 恢复思路；
- 新手适用程度。

可以推荐，但由用户选择。不要在方案阶段提前执行改变状态的命令。

## 单步执行

获得授权后：

1. 复述选择和本步目标；
2. 只执行一个会改变状态的原子操作；
3. 读取真实结果；
4. 状态与预期不同就停止原方案并重新诊断；
5. 冲突发生后先查看冲突范围，再逐个判断业务语义。

给用户手动命令时说明操作系统、影响范围、预期现象、常见异常和需要返回的必要输出。默认请求关键错误与末尾 10～30 行；敏感值必须遮盖。

## 验证收尾

操作完成后重新检查：

- branch 与 HEAD；
- 工作区和暂存区；
- 是否遗留 Git 操作；
- 本地与上游关系；
- 目标提交或远端引用是否符合预期。

最后说明完成了什么、没有动什么、剩余风险和下一步。Session 需要收尾时使用 `$session-handoff`，不要在 Git Skill 中维护另一套交接格式。
