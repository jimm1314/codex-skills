# 大模型测评结果分析

## 坚守分析原则

1. 先确认数据口径，再计算指标。不得根据列名猜测字段含义、正负标签、分母、权重、版本关系或通过标准。
2. 始终区分：
   - **已确认事实**：数据或实验记录直接支持；
   - **数据支持的推断**：有统计证据但尚未完成因果验证；
   - **待验证猜测**：需要日志、对照实验或人工复核。
3. 不把相关性、同时发生或版本差异直接写成因果关系。
4. 同时报告分子、分母、缺失量、效应大小和不确定性；小样本不得下确定性结论。
5. 默认只读原始文件。除非用户明确要求，不修改、覆盖、清洗后回写或删除原始数据；新结果写入单独文件。
6. 本地处理公司日志和测试数据。未经允许，不上传到外部服务，不调用外部 Judge，不把原始内容发给第三方。
7. 展示案例前遮盖姓名、手机号、邮箱、密钥、Token、内部地址、账号和其他可识别信息。不能可靠脱敏时只展示案例 ID 与统计摘要。

## 第一步：确认数据合同

在读取或计算前确认：

1. 数据来源、文件格式、文件列表、工作表、编码和生成时间；
2. 一行代表一次执行、一个样本、一个评分还是聚合结果；
3. 样本唯一 ID、重复运行 ID 和配对键；
4. 每个关键字段的含义、类型、单位和允许值；
5. 通过、失败、跳过、错误和缺失如何定义；
6. 模型、Prompt、参数、知识库、工具和系统版本；
7. 实验组、对照组以及唯一被改变的变量；
8. 总体、维度和业务场景的评分口径、权重与通过标准；
9. 人工评分、规则评分、自动评分和 Judge 评分分别来自哪里；
10. 数据处理权限、脱敏要求和允许的输出位置。

信息不足时每次只问最关键的 1～3 个问题，并提供选项。优先使用：

> 每一行代表什么？  
> A. 一个测试样本的一次执行  
> B. 一个样本的多次执行汇总  
> C. 一个维度或版本的聚合结果  
> D. 其他，请用一句话说明

> 哪个字段表示最终结果？  
> A. 通过/失败状态  
> B. 数值分数  
> C. 两者都有  
> D. 目前没有统一结果字段

如果用户提供公司数据，先提醒确认是否有权在当前环境处理，以及是否允许使用本地脚本；在得到答案前不要将数据发送到任何外部服务。

## 第二步：检查数据范围和质量

阅读 [analysis-methods.md](references/analysis-methods.md)，检查：

1. 文件能否完整读取、Schema 是否一致、字段类型是否符合数据合同；
2. 总行数、唯一测试样本数、有效执行数及其差别；
3. 完全重复、主键重复、重复运行和跨版本配对情况；
4. 各字段及各版本的缺失率，区分真实缺失、跳过、不适用和解析失败；
5. 越界分数、非法标签、时间异常、极端值和不可能组合；
6. 版本、维度、场景、语言、严重程度和失败类型的样本分布；
7. 评分规则、权重、Judge、标注员和数据 Schema 是否在实验中途变化；
8. 选择偏差、过滤偏差、数据泄漏、组间不平衡和覆盖空白。

不要未经确认直接删除异常记录或填补缺失值。分别报告：

- 原始记录数；
- 纳入分析的记录数；
- 排除或无法使用的记录数；
- 每条排除规则和受影响数量。

字段口径确认后，可使用只读脚本 [profile_evaluation_results.py](scripts/profile_evaluation_results.py) 生成确定性数据概况。先运行 `--help`，显式传入字段映射和通过/失败值。脚本不负责理解业务含义，也不能替代人工确认。

## 第三步：计算核心指标

按数据可用性计算并明确分母：

1. 总样本数、唯一样本数、执行次数；
2. 成功数、失败数、跳过数、错误数及对应比率；
3. 总体分数以及均值、中位数、分位数和分布；
4. 各能力维度、业务场景、语言、严重程度和失败类型的结果；
5. 宏平均、微平均或加权平均，并说明选择理由；
6. 人工评分与自动评分差异；
7. Judge 与人工的一致率、混淆情况和一致性指标；
8. 需要人工复核的案例数量和原因；
9. 未覆盖或样本不足区域。

比例附带置信区间；连续分数报告分布，不只报告均值。缺失值不得悄悄进入失败或成功分母。

## 第四步：对比版本和实验组

1. 明确对照组、实验组和发生变化的模型、Prompt、参数、数据、工具或系统版本。
2. 同一测试 ID 在两个版本都有结果时优先做配对比较；无法配对时说明组间样本差异。
3. 同时报告：
   - 两组样本量和基线值；
   - 绝对差值与百分点变化；
   - 相对变化；
   - 置信区间、效应大小和适当的显著性检验；
   - 改善数、退化数、无变化数；
   - P0/P1 或高严重度的新失败。
4. 多维度、多模型反复比较时提醒多重比较风险。
5. 将结论分为“可靠提升”“可靠退化”“方向性变化但证据不足”“未观察到可靠差异”。
6. 不把“没有统计显著差异”解释成“两者完全相同”，也不把统计显著自动等同于业务重要。

## 第五步：分析评分一致性

1. 分清人工、规则、自动指标和 LLM Judge 的量表及版本。
2. 分类标签使用一致率、混淆矩阵和 Cohen's kappa 等；有序评分使用加权 kappa；连续评分结合误差、相关性和系统性偏差。
3. 不仅报告相关系数。高相关仍可能存在固定偏高、固定偏低或关键类别错判。
4. 分维度、分严重程度和分分数区间检查不一致。
5. 将以下案例列入人工复核：
   - P0/P1 失败；
   - 人工与自动评分冲突；
   - 多个 Judge 不一致；
   - Judge 低置信或边界分数；
   - 引用、工具轨迹或系统日志与最终评分矛盾；
   - 可能包含敏感信息或评测污染。
6. 明确 LLM-as-a-Judge 的位置偏差、冗长度偏差、自偏好、Prompt 敏感性、版本漂移和不稳定性。

## 第六步：归类和聚合失败模式

阅读 [failure-attribution-and-reporting.md](references/failure-attribution-and-reporting.md)：

1. 优先使用已定义且口径稳定的失败标签；
2. 对无标签失败先提取可观察症状，再形成候选主题；
3. 聚类后人工检查主题名称、边界、混合类别和“其他”类别；
4. 同时按频率、严重程度、版本新增、业务影响和可修复性排序；
5. 区分故障发生点、传播路径、根因候选和根因确认状态；
6. 至少考虑模型能力、Prompt、RAG 检索、上下文截断、工具选择、参数生成、工具执行、工作流编排、系统接口、测试数据、评分规则和 Judge 偏差。

只看到最终输出时不能确认 RAG、工具或系统根因。需要检索轨迹、上下文、工具调用、系统日志或隔离实验支撑。

## 第七步：选择代表性案例

从以下类别分层选择，而不是只挑最醒目的失败：

1. 高频典型失败；
2. 低频但高严重度失败；
3. 新版本新增回归；
4. 明显改善案例；
5. 人工与自动评分分歧案例；
6. 根因不明确、最需要补证据的案例；
7. 能代表覆盖空白或数据质量问题的案例。

为每个案例提供脱敏后的案例 ID、场景、预期、实际表现、证据、严重程度、影响范围、归因状态和建议验证动作。没有权限时不要展示原始输入输出。

## 第八步：形成结论和行动

1. 将修复建议按“业务影响 × 频率 × 严重程度 × 证据可信度 × 修复成本”排序。
2. 为每个建议指定目标层、依据、预期收益、验证方式和回归用例。
3. 对证据不足的问题优先建议补日志、补样本或做单变量对照实验，而不是直接改模型或 Prompt。
4. 向负责人汇报时先写 3～5 条简洁结论：发生了什么、是否可信、影响什么、最优先做什么。
5. 明确列出不能从当前数据得出的结论。

## 组织最终输出

严格按以下顺序输出：

1. 执行摘要；
2. 数据范围和质量；
3. 核心指标；
4. 分维度结果；
5. 版本对比；
6. 失败模式；
7. 代表性案例；
8. 可能的根因；
9. 风险和结论限制；
10. 修复优先级；
11. 下一轮测评建议。

如果字段口径或数据权限尚未确认，只输出当前理解、数据风险和 1～3 个待确认问题，不提前计算。大型结果分层展示，正文保留决策信息，详细表格另存到新文件。

## 决定是否使用多 Agent

1. 小型文件、单版本或少量指标默认使用单 Agent。
2. 只有数据量大、版本多、任务可独立拆分且环境允许时，才分别委派：
   - 数据质量检查；
   - 指标计算；
   - 失败模式分析；
   - 版本与实验组对比。
3. 给各子任务同一份只读数据快照和统一数据合同；子任务不得分别修改同一份原始数据。
4. 由主智能体统一分母、缺失值、权重、版本、显著性和优先级口径，复算关键指标并检查结论冲突。
5. 不为展示复杂度强制使用多 Agent；无法使用时按相同流程单线程完成。
