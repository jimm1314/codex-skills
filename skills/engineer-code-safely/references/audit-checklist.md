## 1. 审计顺序与证据

保持固定顺序：静态通读是前置步骤，之后依次审计五个维度。维度内部可以并行收集互不依赖的证据，最终结论由主智能体统一给出。

每个检查项只能使用以下状态：

- `✅ 已通过`：有代码、测试、构建、扫描或可观察结果支持。
- `⚠️ 存在风险`：当前可以运行，但存在明确条件下会触发的风险或限制。
- `❌ 未通过`：不满足需求，或存在交付前必须修复的问题。
- `⏳ 尚未验证`：受环境、权限、网络、依赖、数据或外部服务限制，缺少验证证据。
- `➖ 不适用`：当前任务不存在该风险场景；说明判断依据。

不得为使报告好看而全部标为通过。静态阅读只能支持静态结论，不能替代运行、性能或漏洞验证。

## 2. 静态通读（前置）

完整阅读本次差异及直接相关调用代码，检查：

- 命名是否含糊，控制流是否跳跃；
- 是否重复实现已有逻辑；
- 返回值或异常是否被忽略；
- 是否存在隐藏副作用或超出需求的修改；
- 配置、默认值、注释与实现是否一致；
- 用户原有未提交修改是否被覆盖；
- 测试是否真正断言业务结果，而非只检查状态码或无异常。

使用 Git 时核对工作树状态和实际差异；不要把任务开始前已有变更算作本次交付。

## 3. 安全性

按真实攻击面检查：

- 外部输入的类型、长度、枚举、格式和业务约束；
- SQL、命令、路径、模板、反序列化和 XSS 注入；
- 身份认证、对象级/操作级授权和最小权限；
- Token、密码、密钥、连接串及内部地址是否硬编码或泄露到日志；
- 文件名、扩展名、大小、内容、存储路径和目录穿越；
- 传输加密、敏感字段脱敏和数据保留；
- 新增或变更的第三方依赖及供应链风险。

仅在实际执行依赖安全扫描或查询可靠且当前的漏洞来源后，才可写“未发现已知 CVE”。否则标记 `⏳ 尚未验证` 或说明“需要依赖安全扫描”。扫描结果也要注明工具、时间、数据库可用性和覆盖范围。

## 4. 完整性

逐项对照 Spec 和验收标准检查：

- 所有承诺的功能点是否实现；
- 正常路径、主要异常路径和边界条件是否覆盖；
- 未传、`null`、空字符串、零值、负值、超长输入和最大值是否按契约处理；
- 必要配置、依赖清单、环境变量示例和启动入口是否同步；
- 数据库结构、迁移、初始化、数据修复和回滚是否需要且完整；
- 文档、示例请求和测试夹具是否与实现一致。

把每条验收标准映射到代码位置和验证证据；没有证据的标准不得标为通过。

## 5. 稳定性

根据实际场景检查：

- 网络、文件、数据库和外部服务异常是否被明确处理；
- 超时是否存在且合理；重试是否只用于幂等、短暂失败的操作；
- 多个必须同时成功的数据操作是否需要事务，事务边界是否正确；
- 是否存在共享资源并发竞态，锁或原子操作是否必要且粒度合理；
- 文件、连接、游标、线程、进程和内存是否可靠释放；
- 日志是否足以定位问题且不泄密；
- 是否存在合理的降级、恢复或重新执行方式。

没有网络、并发、事务或长期资源等场景时标记 `➖ 不适用`，不得为了通过审计强行增加复杂设计。

## 6. 关联性与一致性

沿真实调用链核对：

- 调用方与被调用方的参数名、类型、必填性、默认值和返回结构；
- API 状态码、错误格式与客户端处理；
- 数据模型、序列化格式、数据库字段和迁移；
- 前端、后端、任务脚本、Agent 工具 schema 和外部系统契约；
- 模块依赖方向、循环依赖和初始化顺序；
- 语言、运行时、框架、依赖和部署环境版本兼容性；
- 旧调用方是否需要兼容层、版本控制或同步发布。

接口一侧的测试通过不代表端到端契约一致；至少使用契约测试、集成测试、示例载荷或逐字段静态核对提供证据。

## 7. 可维护性与扩展性

检查：

- 是否遵守项目命名、格式、错误处理和目录约定；
- 函数、类和模块是否职责清楚，是否出现上帝函数；
- 注释是否解释设计原因并与实现一致；
- 测试名称、准备数据、断言和失败信息是否可读；
- 环境相关配置是否外置，敏感值是否由安全配置注入；
- 是否存在可消除而不扩大范围的重复逻辑；
- 扩展点是否来自真实需求，抽象层、模式、线程池或监控是否过度设计。

不要借“可维护性”之名重构无关模块；把非阻塞改进作为后续建议。

## 8. 问题处理闭环

发现 `❌ 未通过`：

1. 定位受影响的需求、代码和验证。
2. 在授权范围内优先实施最小安全修复。
3. 重跑直接验证和必要回归。
4. 重新执行受影响维度的审计并更新证据。
5. 无法安全修复时停止，说明阻塞、影响和需要的用户决策。

发现 `⚠️ 存在风险`：

- 说明风险内容；
- 说明触发条件；
- 判断当前是否阻塞交付；
- 给出具体后续动作、负责人或验证方式（能够确定时）。

## 9. 报告模板

```markdown
## 静态通读结果
- 检查范围：[文件/调用链]
- 发现与处理：[问题、修复或无发现]
- 证据：[git diff、文件位置、静态检查]

## 五维审计报告

| 维度 | 检查项 | 状态 | 证据或说明 | 修复/后续建议 |
|---|---|---|---|---|
| 安全性 | | ✅/⚠️/❌/⏳/➖ | | |
| 完整性 | | ✅/⚠️/❌/⏳/➖ | | |
| 稳定性 | | ✅/⚠️/❌/⏳/➖ | | |
| 关联性与一致性 | | ✅/⚠️/❌/⏳/➖ | | |
| 可维护性与扩展性 | | ✅/⚠️/❌/⏳/➖ | | |

总体结论：[可以交付 / 可以交付但存在非阻塞风险 / 暂不建议交付 / 因环境限制无法确认]
```

按需为一个维度添加多行，确保关键检查项有独立状态。不要用一条笼统的“全部正常”覆盖多个风险。
