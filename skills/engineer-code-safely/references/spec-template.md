## 1. 使用方式

- B 级任务使用简版 Spec，并保留与任务相关的契约、验收和风险。
- C 级任务使用完整 Spec。在高风险、不可逆或架构级决策确认前，不进入实现。
- 只填写有证据或有实际风险的内容。不知道的内容标为“待确认”，采用默认值的内容标为“假设”。
- 把验收标准写成可观察、可执行或可测量的结果，避免“运行正常”“体验良好”“性能较高”。

### 文件结构

```text
[项目根目录]/
├── path/existing-file.ext    # 修改：职责
├── path/new-file.ext         # 新增：职责
└── path/obsolete-file.ext    # 删除：依据（须获授权）
```

不要为了展示完整而列出无关文件。删除必须说明依据和授权状态。

### 数据流与调用链

只画实际存在的层级，例如：

```text
用户操作 → 前端组件 → API 路由 → Service → 数据访问层 → 数据库

                                 外部模型/工具
```

为每个箭头说明数据格式、错误如何返回，以及调用方和被调用方是否同步修改。

## 6. 实施任务

按依赖顺序拆分为小而可验证的任务：

| 任务 | 目标 | 文件 | 前置依赖 | 修改内容 | 验证命令及证明目标 | 完成标准 | 风险 |
|---|---|---|---|---|---|---|---|
| T-01 | | | 无 | | | | |

- 不在前置依赖未满足时盲目进入下一任务。
- 每个阶段完成后运行最小相关验证；最后运行集成验证和回归检查。
- 命令无法运行时记录阻塞因素和替代证据，不得填写虚构结果。

## 7. 确认闸门

必须等待用户确认：

- 会改变公开接口或破坏旧版本兼容；
- 会删除或不可逆迁移数据；
- 会明显改变架构、技术栈或部署方式；
- 涉及生产环境、真实敏感数据或危险操作；
- 多种选择会实质改变范围、成本或安全性，且无法从项目规则得出答案。

可以记录假设后继续：

- 命名、局部文件组织等低风险且易撤销选择；
- 项目已有明确惯例可直接沿用；
- 不影响公开契约和验收标准的实现细节。
